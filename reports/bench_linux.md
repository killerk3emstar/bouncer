# Benchmark in a Linux container (real T1, ONNX on CPU)

Run on 2026-10-04 in Docker Desktop 29.8 (linux/arm64 VM on an Apple M4 Pro), container limited to 4 CPUs (`--cpus 4`), image built from `Dockerfile`, `python scripts/bench.py --quick --t1 onnx` (25 measured requests per scenario, so treat the p50 values as indicative). Command:

```
docker build -t bouncer:local .
docker run --rm --cpus 4 -v $PWD/models:/app/models:ro bouncer:local python scripts/bench.py --quick --t1 onnx
```

Compared with the native run in reports/bench.md: about 2x the T1 time at 4 CPUs (short prompt p50 20 ms vs 10.5 ms, 2 KB prompt 221 ms vs 84 ms) and 73 req/s instead of 187-195. Without T1 the gateway adds 1.3 ms and serves 590 to 775 req/s. On a Linux server, T1 throughput scales with the cores given to the gateway, the number of gateway workers or replicas, and `T1_CONCURRENCY` (default 3).


Generated by `scripts/bench.py --quick` on 2026-10-04 04:24:57 UTC (28.2 s wall time).

## Setup

- Hardware: aarch64, 8 GB, Linux-7.0.14-linuxkit-aarch64-with-glibc2.41; Python 3.12.15, onnxruntime 1.30.0.
- Machine load average before / after: [0.0, 0.0, 0.0] / [0.83, 0.21, 0.07] (the Mac is shared with another project, so absolute numbers carry noise).
- Gateway: `python -m bouncer.gateway.app`, one uvicorn worker, policy = `policy/bouncer.yaml` with upstreams pointed at the mock, judge backend `fake` (in-process, no model), team budgets raised so they never trigger, hot reload off.
- T1: `onnx` (protectai/deberta-v3-base-prompt-injection-v2, ONNX fp32 on CPU).
- T2: the fake judge answers in-process, so the `t2` column is near zero. Real judge latency is measured separately (`judge/bench.py`, `reports/judge_bench_*.json`).
- Upstream: `demo/mock_upstream.py` (simulated OpenAI API, no model) on the same machine.
- Client: a minimal asyncio HTTP/1.1 keep-alive client in one process (httpx on the client side became the bottleneck at 32 concurrent requests). Latency scenarios: 25 measured requests each after 3 warm-up requests, direct and gateway requests alternate. Every prompt is unique unless noted, so the T1 cache does not hide classifier cost.
- Gateway resident memory after the run: - MB.

## What dominates the overhead

- `benign_short`: gateway overhead p50 18.9 ms, of which T1 18.4 ms (97%) and T0 0.3 ms; the rest (0.2 ms) is request parsing, policy lookup, audit write and proxying.
- `prompt_2kb`: gateway overhead p50 219.4 ms, of which T1 212.9 ms (97%) and T0 3.5 ms; the rest (3.0 ms) is request parsing, policy lookup, audit write and proxying.
- `benign_repeat`: gateway overhead p50 0.2 ms, of which T1 0.0 ms (0%) and T0 0.1 ms; the rest (0.1 ms) is request parsing, policy lookup, audit write and proxying.
- `secret_redaction`: gateway overhead p50 40.9 ms, of which T1 40.0 ms (98%) and T0 0.5 ms; the rest (0.3 ms) is request parsing, policy lookup, audit write and proxying.
- `tool_call_side_effect`: gateway overhead p50 20.5 ms, of which T1 19.0 ms (93%) and T0 0.3 ms; the rest (1.1 ms) is request parsing, policy lookup, audit write and proxying.
- `streaming`: time to first content chunk p50 0.2 ms direct vs 20.3 ms through the gateway. T1 on the prompt accounts for 17.8 ms of that (it runs before the request is forwarded); the rest includes the small window of text the gateway holds back so a secret split across chunks can still be redacted. Output scanning of the stream shows up as T0 (5.4 ms p50 over the whole stream).
- Throughput peaked at 73.1 req/s with 32 concurrent clients (single uvicorn worker, T1 onnx); p95 at that level was 2297.4 ms.
- T1 p50 grows from 18.9 ms at 1 client to 225.2 ms at 32 clients. The ONNX classifier runs at most 3 inferences at once (`T1_CONCURRENCY`, one shared session in `bouncer/t1/classifier.py`), so under load requests queue for it; more workers or replicas scale it further. Without T1 the same path costs well under 1 ms (see `benign_repeat`, where the T1 result is cached).
- With T1 disabled the same gateway serves 775.0 req/s (concurrent clients: 1, p95 1.7 ms); everything except T1 costs 0.4 ms p50 per request inside the gateway (audit `gateway_overhead`).
- Without T1, the next limit is the single worker process: the gateway's own `upstream` time grows from 0.4 ms p50 (concurrent clients: 1) to 22.8 ms (concurrent clients: 32) while the mock answers direct requests at the same concurrency in 2.1 ms p50. The httpx client used for the upstream call degrades the same way under concurrency on the load-generator side (see the RawHTTP note in `scripts/bench.py`). More uvicorn workers or replicas scale this part; budget counters are the only shared state.

## Reproduce

```
make bench                                  # full run
uv run python scripts/bench.py --quick      # about 20-30 s
uv run python scripts/bench.py --t1 fake    # without the ONNX classifier
```

Ports 8705 (gateway) and 8706 (mock) by default; change with `--gateway-port` / `--mock-port`. Raw numbers: `reports/bench.json`.
