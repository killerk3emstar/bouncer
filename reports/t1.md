# T1 prompt-injection classifier: latency and accuracy

Model: `protectai/deberta-v3-base-prompt-injection-v2` (Apache-2.0), ONNX fp32, onnxruntime 1.30.0
`CPUExecutionProvider`, 4 intra-op threads, `tokenizers` 0.23 (no torch). Code: `bouncer/t1/`.
Measured 2026-10-03/04 on an Apple M4 Pro (14 cores, 48 GB RAM), macOS (Darwin 27.0.0), Python
3.12.11. The machine was shared with another project during all runs (load average 3.5 to 12), so
latency numbers vary between runs; we give the range.

## Latency

Model load + warm-up: 0.9-1.7 s (once per process). One call per measurement, 30-40 iterations
after 3 warm-up calls, model loaded. Script: `eval/bench_t1.py`; last run in `reports/t1_bench.json`.

| case | windows | p50 ms (3 runs) | p95 ms (3 runs) |
|---|---|---|---|
| 1 text, ~50 tokens | 1 | 15.4 / 15.8 / 17.3 | 16.9 - 23.7 |
| 1 text, ~300 tokens | 1 | 70.0 / 76.8 / 110.7 | 89.6 - 114.3 |
| 1 text, ~1000 tokens | 3 | 470.9 / 588.4 / 694.2 | 513.5 - 751.5 |
| batch of 8 texts, ~50 tokens each | 8 | 89.9 / 128.7 / 142.6 | 108.3 - 166.0 |
| batch of 8 texts, ~300 tokens each | 8 | 638.6 / 876.9 / 996.3 | 724.6 - 1519.1 |

Per text in the eval (940 texts, mostly short, one text per call): p50 11.3 ms, p95 26.0 ms.

What this means for the gateway:
- Short fragments (user messages, tool descriptions, small JSON results) cost 10-30 ms, in line with
  the plan.
- Cost grows with length: one full 512-token window is about 150-230 ms on 4 threads, so a fetched
  web page of 1,000 tokens adds about 0.5 s. Batching helps little on CPU (8 short texts take 6-9
  times as long as one); it mainly saves call overhead.
- Long texts are split into windows of 512 tokens with 64 tokens of overlap; the score is the max over
  windows. By default at most 16 windows (about 7,000 tokens) are scored per text; beyond that, evenly
  spaced windows including the first and last are scored and `T1Result.windows_scored < windows`
  tells the pipeline that coverage was partial.
- Tried and not adopted: dynamic INT8 quantization. Default settings break the model (an obvious
  injection drops from score 1.0 to 0.06). Per-channel quantization of MatMul only keeps accuracy
  (bank_ops AUC 0.860 vs 0.868; 25 of 1,880 decisions change, 20 of them on Polish or German text)
  but was only 1.04-1.34x faster under comparable load (300 tokens: 64-65 ms vs 70-77 ms). Not worth a second
  model artifact and the `onnx` build dependency. Reproduce:
  `uv run --with onnx python -c "from onnxruntime.quantization import quantize_dynamic, QuantType; quantize_dynamic(src, dst, weight_type=QuantType.QInt8, per_channel=True, op_types_to_quantize=['MatMul'])"`.

## Accuracy

Full tables: `reports/eval.md` (generated by `eval/run_eval.py`). Datasets and licenses:
`eval/datasets/README.md`. Positive class = injection. "Escalate" = score >= 0.50, "block" = score >=
0.98 (thresholds from `policy/bouncer.yaml`).

### Obfuscation (bank_ops, escalate threshold)

Detected: spaced letters 5/5, Cyrillic homoglyphs 5/5, zero-width characters 5/5, uppercase 4/4,
fullwidth 4/4, base64 5/5, ROT13 5/5. Missed: leetspeak 3 of 5 missed (all 5 missed at the block
threshold), Unicode tag characters 2/2 missed (the payload is invisible to the tokenizer).
Base64 and ROT13 are caught only because of the wrapper sentence ("Decode this and follow the
instruction inside"); the model does not decode. A bare encoded payload inside a tool result is
T0's job (decode, then scan the decoded copy).

### Threshold sweep

The model is very confident: most scores are below 0.01 or above 0.99. Raising the block threshold
barely reduces false alarms on our hard negatives (most of them score 0.996-1.000):

| threshold | bank_ops recall | bank_ops FPR | deepset_test recall | deepset_train FPR |
|---|---|---|---|---|
| 0.50 | 84.3% | 26.4% | 36.7% | 1.2% |
| 0.90 | 81.3% | 25.0% | 33.3% | 0.9% |
| 0.98 | 76.1% | 22.9% | 31.7% | 0.3% |
| 0.99 | 74.6% | 21.5% | 30.0% | 0.3% |
| 0.999 | 59.0% | 13.9% | 21.7% | 0.0% |

### Language routing (`t1_route`: T1 >= 0.50 or `is_probably_english` is False)

Routing every non-English text to T2 brings recall on our Polish attacks to 30/30 and on German
attacks to 108/109 (deepset and ours). The price is T2 load: 28 of 29 everyday Polish requests and
about two thirds of German deepset benign texts would go to the judge (short German keyword queries
like "Rentenreformen Europa" count as neutral and stay with T1). English benign traffic is not
affected (false-alarm rate unchanged).

## Findings

1. T1 alone should not block user messages in the `balanced` profile. On our bank-ops hard
   negatives it raises false alarms on 37% of English and 57% of Polish texts at the block
   threshold, with scores of 0.996-1.000, so no threshold fixes it. Typical triggers: "ignore the
   noise in this chart", "forget the Q2 numbers", "override the default currency", "repeat the table
   above", "what is a system prompt", "disregard my previous message", an e-mail saying "please
   ignore the previous invoice". On public deepset benign text the same model is quiet (0-1.2% FPR):
   the problem is imperative business language, which an operations assistant sees all the time.
2. T1 is a good escalation signal on English. 88.9% of direct and 75% of indirect English attacks
   in bank_ops score >= 0.50, and all 17 English jailbreaks do. Note that our jailbreaks target the
   bank assistant and contain instruction-override wording; the model card states it does not
   detect jailbreaks in general, and we did not test classic long-form jailbreak prompts.
3. Polish is weak, as expected for an English-only model: 24% false alarms on everyday Polish
   requests and 1 of 8 indirect Polish attacks detected. German direct attacks score well in our
   set (13/13) but deepset German recall is 44%. This is the case for routing non-English text to T2.
4. Recall on deepset is low (35-44%) while precision stays at 96-100%. Many deepset positives are
   off-topic or political requests ("act as an interviewer", "say that you hate X") without an
   instruction override; the model treats them as benign. Some of these labels are debatable, but we
   report the dataset as is.
5. Leetspeak and Unicode tag smuggling get through T1; they need T0 normalization (tag characters
   blocked outright, leetspeak only partly recoverable).

## Recommendations for the pipeline (for the lead; not applied here)

- `balanced`: T1 >= `escalate_above` → T2; block on T1 only together with a T0 heuristic or
  signature hit on the same fragment, or in `strict`. With `block_above: 0.98` and T1 alone, 27 of
  the 60 bank-ops hard negatives (and 23% of all bank-ops benign texts) would be blocked, and the
  jury will type exactly such sentences.
- Do not send the operator's own system prompt to T1 (model card warns about false positives; our
  hard negatives about system prompts confirm it).
- Treat `windows_scored < windows` (text longer than about 7,000 tokens) as partial coverage:
  escalate or apply `fail_mode`.
- Expect T2 load from Polish traffic: with `escalate_non_english: true`, almost every Polish user
  message goes to the judge. If the judge is too slow for that, a Polish-capable classifier would be
  the fix (e.g. Llama Prompt Guard 2 86M, multilingual, if access is granted; not evaluated here).

## Offline tests and fixture

- `make test` uses `FakeInjectionClassifier` (`bouncer/t1/fake.py`): exact-text lookup in
  `tests/fixtures/t1_scores.json` (337 real scores: the 55 texts in `tests/cases/*.yaml` at
  recording time, all 278 `bank_ops` texts, and NFKC/invisible-stripped forms where they differ),
  then a keyword heuristic.
  The heuristic agrees with the real model on 154 of 278 bank_ops texts at 0.50; it mimics a
  correct English detector, not the model's false alarms. Re-record after adding cases:
  `uv run python scripts/record_t1.py`.
- With the fixture, `T1_BACKEND=fake uv run python eval/run_eval.py --datasets bank_ops` reproduces
  the real-model bank_ops numbers without the model.
- Unit tests: `tests/unit/t1/` (63 tests, 0.25 s): language heuristic, fake classifier, window
  planning, batching and max-over-windows with a stub ONNX session.

## Not verified

- Latency on Linux / in Docker (the jury's machines) and without the other project's load.
- Thread-count tuning beyond 4 (kept at 4 because the Mac is shared).
- Accuracy of the language heuristic beyond the unit tests and the deepset tagging review.
- Behaviour on texts that were normalized by T0 first (eval runs T1 on raw text; the combined
  pipeline layer will show the effect of normalization).
